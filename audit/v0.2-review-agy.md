# Edu v0.2 — Cross-Review & Audit Report (Plugin-First)

**Auditor:** helper (Antigravity)  
**Date:** 2026-10-09  
**Scope:** `docs/ARCHITECTURE.md` §16, `README.md`, `src/crew/`, `src/setup/`, `src/mcp/`, `scripts/build-plugins.ts`, `plugins/`, `.claude-plugin/`, `.agents/plugins/`, `src/tui/`  
**Verdict:** **`ship-with-fixes`**

---

## Executive Summary

Edu v0.2 represents a major architectural leap forward, pivoting from monolithic CLI adapters to native, plugin-first integrations across Claude Code, OpenAI Codex, Pi, OpenCode, and Google Antigravity. It delivers multi-vendor crew orchestration (both headless and via Herdr terminal panes), an interactive mission-control TUI (`edu watch`), and MCP-based memory tools.

However, several critical and high-severity issues across **Security**, **Correctness**, and **Product Discoverability** must be addressed before general availability:
1. **Security:** Codex plugin configuration globally auto-approves all MCP tools (`default_tools_approval_mode: "approve"`), allowing autonomous prompt injections to invoke `edu_crew_dispatch` with full execution autonomy and arbitrary `cwd` without human consent.
2. **Correctness:** Herdr pane jobs stall permanently in `edu watch` because `fsCrewSource` never triggers pane status refreshes and Herdr pane executions do not stream events into `.jsonl` files.
3. **Correctness / Boundaries:** Antigravity environment detection is missing from MCP caller inspection, defeating the cross-vendor guarantee for Antigravity users during code reviews.
4. **Lifecycle:** Setup uninstallation is fragile: any failure in a single CLI installer throws an exception, aborting before removing managed configuration blocks or unlinking manifests.
5. **Product / Usability:** README manual marketplace installation instructions bypass global setup, resulting in missing brain initialization (`~/.edu`) and omitted Codex identity blocks.

## 1. Top Evidenced Findings (Ranked by Severity)

### Finding 1 (CRITICAL / SECURITY): Codex MCP server opts in to global auto-approval, exposing code execution via `edu_crew_dispatch`
- **Location:** [`plugins/codex/.mcp.json:8`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/plugins/codex/.mcp.json#L8), [`scripts/build-plugins.ts:49`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/scripts/build-plugins.ts#L49)
- **Failure Scenario:**
  In `plugins/codex/.mcp.json`, the generated server entry specifies:
  ```json
  "default_tools_approval_mode": "approve"
  ```
  In Codex CLI, this directive auto-approves all tool calls from the `edu` MCP server without requesting interactive human approval.
  While read-only retrieval tools (`edu_brief`, `edu_recall`, `edu_read`) benefit from seamless invocation, the `edu` server ALSO registers state-modifying tools and, crucially, **`edu_crew_dispatch`** ([`src/mcp/server.ts:143-149`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/mcp/server.ts#L143-L149)).
  `edu_crew_dispatch` can launch background detached processes or open terminal panes running any installed coding CLI (`claude`, `codex`, `pi`, `opencode`, `agy`) with `autonomy: "auto"` or `autonomy: "full"`, executing arbitrary tasks in any directory. Under this configuration, an LLM subject to indirect prompt injection or running unattended can spawn uncontained child agents with full execution privileges without any human approval prompt.
- **Suggested Fix:**
  Remove `default_tools_approval_mode: "approve"` from the generated `plugins/codex/.mcp.json`, or if auto-approval is required for non-interactive test runs, configure Codex approval overrides per-test rather than shipping a blanket auto-approval in the default plugin distribution. Alternatively, gate `edu_crew_dispatch` behind explicit permission checks.

### Finding 2 (HIGH / CORRECTNESS & USABILITY): Pane jobs stall permanently in `edu watch` (Missing pane refresh and events)
- **Location:** [`src/cli/commands/watch.ts:27-31`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/cli/commands/watch.ts#L27-L31), [`src/tui/crew.ts:52-70`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/tui/crew.ts#L52-L70), [`src/crew/herdr.ts:75-107`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/crew/herdr.ts#L75-L107)
- **Failure Scenario:**
  1. In `src/cli/commands/watch.ts`, `edu watch` creates an `fsCrewSource(ws.primary.root)`.
  2. In `src/tui/crew.ts`, `fsCrewSource.list()` only reads `.json` files on disk via `readJob()`.
  3. In `src/crew/herdr.ts`, pane state transitions (`running` -> `done` / `failed`) are computed solely within `refreshPane(job)`, which is ONLY invoked when an external caller triggers `crew.status()` or `crew.result()`. `fsCrewSource` never calls `refreshPane`.
  4. Furthermore, `herdr.ts` never appends events to `<jobId>.jsonl` (`store.appendEvent` is never called for pane jobs).
  5. As a consequence, when a user dispatches a job in `pane` mode (e.g., via `/edu:crew --pane` or `edu_crew_dispatch { mode: 'pane' }`), `edu watch` picks up the initial record with `status: 'running'`. When the Herdr agent completes or fails in the split pane, `<jobId>.json` on disk is never refreshed by the watcher. `edu watch` shows the agent as running indefinitely, and `<jobId>.jsonl` remains empty.
- **Suggested Fix:**
  - In `src/tui/crew.ts` or `src/cli/commands/watch.ts`, integrate a live refresher that calls `refreshPane()` for active pane jobs during polling.
  - In `src/crew/herdr.ts`, stream observed status and pane output lines as `EduEvent`s into `store.appendEvent(job.id, ...)` so `edu watch` renders live output instead of an empty pane.

### Finding 3 (HIGH / SECURITY): Unconstrained `cwd` parameter in `edu_crew_dispatch` permits arbitrary filesystem targeting
- **Location:** [`src/mcp/server.ts:144-147`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/mcp/server.ts#L144-L147), [`src/crew/index.ts:42`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/crew/index.ts#L42)
- **Failure Scenario:**
  `edu_crew_dispatch` accepts `cwd: z.string().optional()`.
  In `src/crew/index.ts:42`:
  ```ts
  const job = await store.create({
    cli: input.cli,
    task: input.task.trim(),
    mode: availablePane ? 'pane' : 'headless',
    cwd: resolve(input.cwd ?? process.cwd()),
    autonomy: input.autonomy ?? 'ask'
  });
  ```
  Neither `server.ts` nor `src/crew/index.ts` validates that the resolved `cwd` is within the project root, workspace boundary, or allowed directory. A caller can pass `cwd: "/"` or `cwd: "../../sensitive-dir"`, and the resulting worker process will spawn in that directory with the specified autonomy.
- **Suggested Fix:**
  Validate that `resolve(input.cwd)` is contained within the current workspace root or one of the configured `BrainLocation` roots, rejecting paths that escape project boundaries.

### Finding 4 (HIGH / CORRECTNESS & SPEC DEVIATION): Caller CLI detection omits Antigravity, breaking cross-vendor review guarantee
- **Location:** [`src/mcp/server.ts:165-171`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/mcp/server.ts#L165-L171), [`src/crew/index.ts:67-68`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/crew/index.ts#L67-L68)
- **Failure Scenario:**
  `detectCallerCli(env)` inspects environment variables for `CLAUDECODE`, `CODEX_`, `PI_`, and `OPENCODE`. It does not check for any Antigravity indicators (such as `ANTIGRAVITY`, `ANTIGRAVITY_AGENT`, or `GEMINI_CLI`).
  When an Antigravity user calls `edu_crew_review` (e.g., via the `edu-review` skill), `detectCallerCli` returns `undefined`.
  In `src/crew/index.ts:67`:
  ```ts
  const reviewer = input.cli ?? available.find(cli => cli !== input.callerCli);
  ```
  Since `callerCli` is undefined, `available.find()` can pick `agy` itself if it is the first available CLI. An Antigravity agent requesting a cross-vendor second opinion receives a review from another Antigravity instance, directly violating ARCHITECTURE.md §16.4 ("Dispatches a read-only reviewer on git diff <base> to a vendor different from the caller when available").
- **Suggested Fix:**
  Add detection for Antigravity environment variables in `detectCallerCli(env)` (e.g., checking `env.ANTIGRAVITY || env.ANTIGRAVITY_AGENT || env.GEMINI_CLI`).

### Finding 5 (MEDIUM / ROBUSTNESS): Uninstall aborts on single CLI failure, leaving managed blocks orphaned
- **Location:** [`src/setup/index.ts:231-239`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/setup/index.ts#L231-L239)
- **Failure Scenario:**
  In `uninstallSetup`:
  ```ts
  for (const cli of manifest.native) {
    for (const command of commands[cli](manifest.packageRoot)) {
      const result = await runner(command);
      if (result.exitCode !== 0) throw new Error(`${command.command} ${command.args.join(' ')} failed: ...`);
    }
  }
  if (manifest.adapterManifestPath) await uninstall({ manifestPath: manifest.adapterManifestPath, force: options.force });
  await (await import('node:fs/promises')).unlink(path);
  ```
  If a user has uninstalled one CLI (or manually removed a plugin in Claude Code or Codex prior to running `edu uninstall`), `runner(command)` exits with non-zero.
  `uninstallSetup` throws immediately. Because the function aborts:
  1. The remaining native CLIs in `manifest.native` are never uninstalled.
  2. Line 237 (`uninstall({ manifestPath: manifest.adapterManifestPath })`) is never reached, leaving all managed instruction blocks (`~/.codex/AGENTS.md`, `~/.config/opencode/AGENTS.md`) and configuration files in place.
  3. Line 238 (`unlink(path)`) is skipped, leaving the setup manifest behind.
  Additionally, `uninstallSetup` does not remove the marketplaces added during setup (`claude plugin marketplace add` and `codex plugin marketplace add`), leaving stale marketplace definitions.
- **Suggested Fix:**
  Wrap each CLI uninstallation in a `try...catch` block to collect errors and warn rather than prematurely throwing, add marketplace removal commands for Claude and Codex, and ensure `manifest.adapterManifestPath` cleanup executes reliably.

### Finding 6 (MEDIUM / CORRECTNESS): Orphan panes leaked on `dispatchPane` startup errors and job completion
- **Location:** [`src/crew/herdr.ts:44-72`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/crew/herdr.ts#L44-L72), [`src/crew/herdr.ts:95-106`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/crew/herdr.ts#L95-L106)
- **Failure Scenario:**
  1. In `dispatchPane`, `runner(['pane', 'split', ...])` successfully creates a new Herdr pane. If the subsequent `runner(['agent', 'start', ...])` fails with an unexpected error (e.g., CLI binary missing or process crash), the `catch` block updates the job status to `failed` and returns. No call to `runner(['pane', 'close', paneId])` is made, leaving an empty, orphaned pane open in the terminal multiplexer.
  2. Once a pane job completes or fails, neither `refreshPane` nor `dispatchPane` sends an agent termination or cleanup command to Herdr, leaking background agent processes.
- **Suggested Fix:**
  Track `paneId` in `dispatchPane` and invoke `runner(['pane', 'close', paneId])` in the error recovery handler if agent startup fails. Provide a clean exit command when jobs terminate.

### Finding 7 (MEDIUM / ARCHITECTURE): MCP roots rebinding race and missing brain initialization on rebound workspace
- **Location:** [`src/mcp/server.ts:36-43`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/mcp/server.ts#L36-L43), [`src/mcp/stdio.ts:15-29`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/src/mcp/stdio.ts#L15-L29)
- **Failure Scenario:**
  In `createEduMcpServer`:
  ```ts
  let bound: Promise<void> | undefined;
  const bind = () => (bound ??= (async () => {
    const locations = await opts.resolveLocations?.(server).catch(() => undefined);
    if (!locations?.length) return;
    brain = openBrain(locations);
    crew = createCrew({ ...opts.crewOptions, locations });
    eduMdPath = join(locations[0]!.root, 'EDU.md');
  })());
  ```
  1. Caching: `bound ??=` memoizes the promise permanently on the first tool call. If the MCP client has not yet responded to `roots/list`, or if the request times out or errors once, `bound` permanently resolves to `undefined`. Future tool calls will never retry rebinding.
  2. Brain Initialization: In `stdio.ts:16-17`, `brain.init(locations[0]!)` was executed for the initial directory (e.g. plugin directory). When `bind()` switches `brain = openBrain(locations)` to the client's actual workspace, it does not call `await brain.init(locations[0]!)`. If the workspace root lacks `.edu`, subsequent brain operations may fail due to missing directories.
- **Suggested Fix:**
  Only cache successful rebinding in `bound`; if `resolveLocations` returns `undefined`, permit subsequent attempts. Call `await brain.init(locations[0]!)` upon rebinding to new workspace locations.

### Finding 8 (MEDIUM / PORTABILITY): `build-plugins.ts` produces false-positive drift on Windows due to unnormalized CRLF reads
- **Location:** [`scripts/build-plugins.ts:109-120`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/scripts/build-plugins.ts#L109-L120)
- **Failure Scenario:**
  `add()` in `scripts/build-plugins.ts` normalizes all generated text to LF (`replace(/\r\n/g, '\n')`).
  However, in `scan()`:
  ```ts
  else if (entry.isFile()) files.set(key, await readFile(path, 'utf8'));
  ```
  The disk content is read verbatim without newline normalization. On Windows or in environments where git checks out files with CRLF (`core.autocrlf = true`), `actual.get(path)` contains `\r\n` while `generated.get(path)` contains `\n`.
  `buildPlugins(..., { check: true })` reports drift across all generated files and exits with code 1, causing CI and local verification checks to fail spuriously on Windows.
- **Suggested Fix:**
  In `scan()`, normalize read content with `.replace(/\r\n/g, '\n')` before inserting into `files`.

### Finding 9 (LOW / PRODUCT): README manual install instructions bypass brain initialization and Codex identity
- **Location:** [`README.md:37-45`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/README.md#L37-L45), [`docs/guides/codex.md:16-18`](file:///Users/eduardomoraga/Moragent/04-LAB/edu/docs/guides/codex.md#L16-L18)
- **Failure Scenario:**
  The table in `README.md` lists manual marketplace commands alongside `edu setup`:
  - Claude: `/plugin marketplace add EduardoMoraga/edu` then `/plugin install edu@edu`
  - Codex: `codex plugin marketplace add EduardoMoraga/edu` then `codex plugin add edu@edu`
  If a user runs only these commands without executing `edu setup`:
  1. The global brain (`~/.edu`) is never initialized (`initBrain` never runs). When the user opens their CLI and asks "what do you remember?", the session-start hook finds no `EDU.md` and remains silent.
  2. Codex plugin hooks do not execute; `edu setup` normally handles this by writing a managed instruction block into `~/.codex/AGENTS.md`. Users who install Codex via marketplace only will get neither identity injection nor initial brain setup.
- **Suggested Fix:**
  Clarify in `README.md` that `edu setup` is the required setup command, or explain that manual marketplace installation must be followed by `edu setup` to seed the brain.

## 2. Verdict & Top 5 Must-Fix

**Verdict:** **`ship-with-fixes`**

The plugin-first foundation, multi-vendor engine abstraction, and TUI improvements are well-architected and close to ready. However, the security gap in Codex MCP approval mode and the lifecycle stall in pane monitoring prevent an unqualified `ship`.

### Top 5 Must-Fix
1. **Restrict Codex MCP Approval Scope (Finding 1):** Remove `default_tools_approval_mode: "approve"` from `plugins/codex/.mcp.json`. Execution tools like `edu_crew_dispatch` must not run without human consent.
2. **Fix Pane Job Lifecycle in `edu watch` (Finding 2):** Connect pane status refreshes and event tailing so pane jobs update and stream in `edu watch` instead of stalling permanently in `running`.
3. **Constrain `cwd` in `edu_crew_dispatch` (Finding 3):** Validate that requested working directories do not escape project/workspace boundaries.
4. **Add Antigravity to Caller Detection (Finding 4):** Include Antigravity environment variables in `detectCallerCli` to preserve the vendor-diversity guarantee in code reviews.
5. **Harden `uninstallSetup` (Finding 5):** Catch per-CLI uninstall errors, ensure `adapterManifestPath` cleanup executes, and remove added marketplaces so uninstalls leave a clean host state.
